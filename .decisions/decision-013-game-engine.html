Game Targets: Godot for Games, three.js for the Web

Architecture 🚪 One-way door High stakes

You want to make standalone games in Godot and web apps or browser games in three.js, choosing per project. Good news: the studio already exports glTF, which both load natively, and your baked-material choice (decision 12) produces plain textures that look the same in both. So the real question is how much is shared between the two targets and how much is built twice. That covers assets, material presets, skeletons and animations, checks, level layouts, game code, and the /game skill Claude uses to run and test each one. Each card shows what's shared (green), what you build (red), and where it's weak (amber).

The studio is the single source for everything visual: shapes, baked materials, skeletons, animation clips and checks. Export takes a target flag and writes what each side wants: a Godot import script so materials survive reimport, or plain glTF for three.js. Game code is written per project in that engine's own language, which is fine because a web app and a Steam game are different programs anyway. The /game skill gets two back ends with the same commands (run, screenshot, play-test).

Works well when

  • Each project is clearly one or the other
  • You want to reuse assets across both freely
  • Each engine is used the way it's meant to be

Watch out for

  • Two run/test back ends to maintain
  • Shaders (toon, outlines) written twice

But the web build ships the whole engine to the browser, so the first load is slow, and it behaves like a game in a box, not a web page. The case against my pick

Option A doubles the parts Claude has to be good at. That's two game languages (GDScript and TypeScript), two physics systems, two ways to run and screenshot a game, and toon or outline shaders written twice. Agents already fail most at engine-specific structure: in one Godot benchmark the best agent passed only 54% of tasks. Doubling the engines doubles that surface. If most of what you'll make is web, Option C keeps one stack Claude already handles well; if most is games, B keeps one engine and accepts a weaker web story.

This recommendation assumes

  • Projects are usually one or the other (a web app or a standalone game), rarely the same game on both.
  • "Web app" means a real site with normal UI and a 3D view inside, which is three.js's strength and Godot's weak spot.
  • Shared assets carry the most value: shapes, baked materials (decision 12, E) and humanoid skeletons all travel as glTF. three.js loads them as-is; Godot gets an import script so studio-owned materials survive reimport.
  • Option D stays possible later: if you keep wanting the same level in both, add the portable format then.

What the research says

  • Godot is the leading engine for Claude-driven standalone games. Its scenes and scripts are plain text, it has a real command line for import, scripts and export, and it took 47% of GMTK Game Jam 2026 entries. Godot docs Game World Observer
  • three.js is about 170 kB gzipped, and its GLTFLoader is the reference glTF implementation, with full skins, morphs and animations. Driving it with headless Chrome is the same setup that tested the studio's own view. Utsubo Microlink
  • Godot's glTF reimport drops material edits made inside Godot. With the studio owning materials and an import script on the Godot side, nothing is edited in Godot, so nothing is lost. Godot forums
  • Godot 4.4–4.6 added retargeting, spring bones and IK. three.js has SkeletonUtils.retarget and CPU bone transforms, which are enough for automated pose tests on both sides. Godot blog three.js docs
  • AI agents do much better on game tasks when they can see the running game: screenshots raised one model from 41% to 52% on Godot tasks. Both back ends of /game need a screenshot path. GameDevBench

Where experts disagree

"Pick one engine and master it" is standard indie advice, because context switching is expensive. The counter-argument here is that the expensive, AI-hard parts (assets, materials, rigs, checks) are made once in the studio and shared. What stays per engine is ordinary code, which Claude writes in either language. The deciding factor is how often the same project needs both targets: rarely means A, often means D.
