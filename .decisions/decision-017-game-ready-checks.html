Game-Ready Checks and Export Profiles

Architecture 🔁 Two-way door Medium stakes

Today's checks catch furniture problems: floating legs, separate pieces, things below the floor. Games add new rules. Triangle and texture budgets, a collision shape for physics, simpler versions for distance (LODs), bone and weight limits, and proof that the file imports cleanly into Godot and three.js. The question is when those rules run and who owns them. Run them on every step, the way the stool's checks do, and Claude fixes problems while it works. Run them only at export, or leave them to each engine, and problems surface late.

When: budgets on every step · engine round-trip on every export
Each object gets a game profile (for example "godot-desktop" or "web-mobile") that adds budget rules, which show up as checks after every change, exactly like "legs grounded". Collision shapes and LODs are generated as ops, so they update when the shape changes and are reviewable. On export, the file is imported headlessly into Godot and loaded in three.js; any warning fails the export. Claude sees a broken budget the moment it happens and fixes it in the same loop.

Works well when

  • Claude builds most assets; it needs fast feedback
  • Two targets with different budgets

Watch out for

  • Round-trip needs Godot installed for export
  • More checks = slower steps on big assets

The case against my pick

Live game checks make every step heavier and noisier. A prop that's mid-build will fail its triangle budget long before it's finished, the same "everything is failing" problem the studio had before checks learned to say "in progress". And the engine round-trip ties export to having Godot installed and running headless, which is one more moving part to break. If most of what you make in the next months isn't headed for a game, B keeps the studio fast and moves all of this to the moment it matters.

This recommendation assumes

  • Game checks only apply to objects with a game profile; furniture renders and other non-game work stay as they are.
  • Budget checks use the existing "pending" state while an object is still being built, so they don't shout mid-build.
  • Collision shapes and LODs are generated ops (hull/box/capsule; simplified copies), so they're reviewable and update with the shape.
  • The Khronos glTF validator (Option D) runs inside the export in every case.
  • Godot is installed on the machine that exports for Godot; three.js round-trips use the headless Chrome the studio already uses.

What the research says

  • The Khronos validator flags joint/weight inconsistencies; glTF needs skin joints to match their bind matrices, and allows 4 influences per weight set. Khronos
  • Asset pipelines break at the hand-off: Godot drops materials on reimport, Unity silently strips texture features, Unreal mishandles skinned meshes. An automated import test catches these before you do. Godot forums Unreal forums
  • Godot's command line can import a project headlessly and quit (--headless --import). That's the round-trip test's engine half. Godot docs
  • An agent that can verify its own output does much better. In the studio's own benchmark runs, checks caught the collapsed roof and the separate pieces; the window overlapping the door was caught only by a render. bench/TASKS.md
