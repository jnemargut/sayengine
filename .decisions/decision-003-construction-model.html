Each object is a base shape plus an ordered list of non-destructive effects (bevel, array, boolean, subdivide) — the Blender model. Easy for humans to read and easy to build first. But it's a straight line per object: relationships between parts (legs attached to seat, back angle tied to seat depth) have nowhere to live, so semantic edits often turn into hunting through stacks.

Works well when

  • Single-object props and game assets
  • Fastest to implement; familiar to Blender users

Watch out for

  • No cross-object relationships or shared parameters
  • Order-dependent; reordering silently changes results
  • No study found of LLMs editing modifier stacks

A Houdini / Blender Geometry Nodes-style graph: boxes for parameters and operations, wires for data flow. Extremely powerful and procedural — one graph can generate infinite chairs. Humans who know node editors love it. But research found no benchmark of LLMs emitting node graphs directly; even AI material/Houdini systems have the model write code that builds the nodes, and a full node editor UI is a large build.

Works well when

  • Procedural generators (trees, buildings, scatter)
  • Technical artists are the core user
  • Per-node caching makes re-evaluation fast

Watch out for

  • LLMs handle wire/socket graphs poorly when emitted directly
  • Node editor UI is a months-long build on its own
  • Intimidating for "never learned Blender" users

The SolidWorks / Onshape / FreeCAD model: 2D sketches on planes, then features (extrude, fillet, shell) in an ordered history. Gold standard for precise, dimension-driven mechanical parts. But features reference generated faces and edges, which get renumbered when upstream changes — the infamous "topological naming problem" that FreeCAD only partly fixed in 1.0. And it's a poor fit for organic shapes, characters and game assets.

Works well when

  • Mechanical parts, enclosures, manufacturing
  • STEP export and dimension-exact output matter most

Watch out for

  • Topological naming breaks references on edits
  • Needs a B-rep kernel (OCCT) from day one
  • Weak for organic, character, game-asset work

Typed Op Graph + Code View

Ask: "thin the legs, round the seat edge" → 2 parameter commits
// generated, readable view of the stored graph param legRadius = 0.015 // was 0.02 param seatRound = 0.012 // was 0.003 const seat = box("seat", [seatW, 0.04, seatD]) .round(seatRound, edges: "seat.top") const leg = cylinder("leg", legRadius, seatH) const legs = leg.placeAt(seat.corners("bottom", inset: 0.03)) export chair = union(seat, legs, back)
Stored as records
{ id:"op_legs", op:"placeAt", inputs:["op_leg"], anchor:"seat.corners:bottom", params:{ inset:0.03 } }
Same op from a GUI drag
{ tool:"setParam", target:"legRadius", value:0.015, author:"human" }
Named anchors (seat.corners) instead of Face<7> — no topological naming
Construction is a graph of small, typed operations (box, cylinder, round, placeAt, union…) stored as records in your change log, with named parameters and named anchors instead of fragile face numbers. The AI and the human see it as a short, readable program; the GUI emits the exact same ops when you drag a slider. This is the pattern Zoo.dev (KCL), Adam (OpenSCAD) and Onshape's own AI path (FeatureScript) all converged on — but typed and validated rather than free code.

Works well when

  • "Thin the legs" must be a one-parameter change
  • You want AI, GUI and history to share one representation
  • Per-op caching keeps regeneration fast on Manifold

Watch out for

  • You're designing a small language — op vocabulary needs taste
  • Organic/sculpted detail needs an escape hatch ("editable mesh" op)
  • Benchmarks: programs run 85–100% of the time, but geometric correctness is far lower

The case against my pick

"Typed op graph + code view" is really two products — a language and its editor — and language design is where solo projects quietly die. The benchmarks are sobering: even the best models scored only ~0.35 on geometric correctness across formats, and quality collapses on complex topology, so a beautiful representation doesn't guarantee good chairs. For general-purpose work, much of the eventual content (characters, sculpts, scanned meshes) won't be parametric at all, so you may spend months on a construction layer that only covers the "hard-surface" half — where a plain modifier stack (A) would have shipped in a week.

This recommendation assumes

  • Start with ~15–25 ops (primitives, transforms, booleans, round/chamfer, array/placeAt, extrude-profile, mirror) and grow from benchmark failures
  • An editableMesh op exists as the escape hatch: freeze a subgraph into direct mesh edits (level 4)
  • Edits reference named anchors/datums, never generated face indices
  • A visual node view can be added later as another view of the same graph — that's what keeps B open
  • Tripwire: if benchmark tasks keep needing raw mesh escapes for >40% of objects, add a modifier-stack layer for mesh objects

What the research says

  • P3D-Bench (June 2026, 11 frontier models): OpenSCAD-style code was the most balanced format; JSON parameter specs almost always run but score lower on geometry; CadQuery fails to execute most often; best geometric judge score across formats only ~0.35. P3D-Bench
  • CADPrompt: GPT-4 compiles CadQuery 92–96% of the time; visual verify-and-refine improves geometric accuracy ~10–18% more than it improves compile rate. arXiv 2410.05340
  • Quality falls off sharply with complexity: Query2CAD easy 95% → hard ~42%; Text2CAD-Bench reports substantial degradation on complex topology. Query2CAD Text2CAD-Bench
  • LL3M: multi-agent Blender code, ~38 s per localized user edit; without shared code context, edits produced a substantially different asset. LL3M
  • CodeAct: executable code actions gave up to 20% higher success and 30% fewer steps than JSON tool calls on multi-tool tasks. CodeAct
  • Zoo.dev: every point-and-click op generates KCL code; their agent runs a plan → execute → visual-check loop. Zoo · Adam/CADAM: Claude writes OpenSCAD, parameters become sliders. CADAM
  • Topological naming: FreeCAD 1.0 only partly fixed it; advice is to reference datums, not generated faces. Onshape uses deterministic, history-derived IDs. FreeCAD wiki Onshape API
  • Node graphs: no benchmark of LLMs emitting graphs directly; VLMaterial and Houdini work have the model write code that builds nodes. VLMaterial
  • Manifold re-execution cost: ~5 ms (2K tris) to ~660 ms (524K tris) per boolean natively — full re-runs are cheap at moderate detail; cache per op at high detail. Manifold

Where experts disagree

One camp says: let the model write real code (Python/OpenSCAD) — models are trained on it and CodeAct shows code beats tool calls. The other says: free code fails silently (OpenSCAD drops geometry), can't be validated per step, and doesn't round-trip with a GUI — use typed, declarative ops. Option D splits the difference: stored as typed ops, shown as code. Whether the AI edits via code text or typed tool calls is Decision 5.
