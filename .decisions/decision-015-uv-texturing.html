How Studio Materials Become Game Textures

Architecture 🔁 Two-way door Medium stakes

Decision 12 settled the big question: games should look like the studio, with wood grain and glaze baked into textures, and nothing painted by hand. What's left is how. A texture needs UVs, which say where each part of the surface sits on the flat image. The studio has to create those automatically, bake each material in, and check the result. The options trade texture memory, uniqueness and the amount of new code. This one is easy to change later, because export is the only place it lives.

Auto-Unwrap + Bake per Asset

Illustration. Parts unwrapped into islands; grain baked in.
xatlasopen-source unwrapper; the one Godot uses for lightmaps
GPU bakein the studio's view, the renderer that already draws the grain
~0.3–1 MBper prop at 512–1024 px
On export, each asset is unwrapped automatically (xatlas, run in the browser), then the studio's own renderer paints each material's grain, glaze and colour into one texture per asset. New checks keep it honest: even texture density, padding around every island so seams don't bleed, and no stretched areas. Every asset gets unique detail, and because the bake uses the same shader as the studio view, the game looks exactly like the studio.

Works well when

  • You want the game to match the studio
  • Each asset should look individual
  • Works the same for Godot and three.js

Watch out for

  • Texture memory grows with asset count
  • Auto-unwrap seams on characters need care

One Shared Material Atlas

Illustration. Each preset baked once as a tile; parts point at tiles.
1 texturefor the whole game
Simple UVsbox projection into a tile
Repeatssame grain on every walnut part
Bake each material preset once into a tile of one shared texture (a "trim sheet"), and point every part at its tile with simple projection. It uses the least memory, is perfectly consistent, and is how a lot of low-poly games stay tiny. But the grain is identical on every walnut surface, details can't follow a specific shape (like grain running along a curved leg), and tile edges can show on large surfaces.

Works well when

  • Huge numbers of assets, small download
  • Mobile or web where memory is tight

Watch out for

  • Visible repetition; grain ignores shape
  • Less of the studio look survives

No Bake: Port the Shaders

Illustration. Each material becomes code in every engine.
0 texturestiny files
Sharp at any sizeno resolution limit
×3 shadersper material, kept in sync
Skip textures: rewrite each procedural material as a shader in Godot and in your three.js games, and export only a material name and settings. Files stay tiny and surfaces stay sharp up close. But glTF can't carry custom shaders, so every other tool sees plain colours. Every material exists three times in different shader languages, and every new preset means three implementations to keep identical, which is the duplication decision 13 tried to avoid.

Works well when

  • Few materials, huge surfaces (terrain)
  • Very tight download budgets

Watch out for

  • Three copies of every material
  • Plain colours in any other tool

Characters and hero props get A's unique bake. Background pieces and level-kit parts share B's atlas. It's what shipped games end up doing, since memory goes where players look. But it's two export paths to build and test from day one, before you know your asset counts need it.

Works well when

  • Big levels with many repeated pieces
  • You know the memory budget matters

Watch out for

  • Twice the export work up front
  • A setting Claude must choose well per asset

The case against my pick

Unique textures per asset add up. A level with 200 props at 1024 px is a few hundred megabytes of texture memory before compression, which is a real problem for web builds (decision 13) and older hardware. Auto-unwrapping is also least reliable on characters: seams can land across a face or a joint, and baked grain can stretch where a kit character bends. If you expect big levels or many browser games, start with D's split, or at least design A so an atlas mode can slot in.

This recommendation assumes

  • Early projects are small: dozens of assets, not thousands. Memory isn't the first constraint.
  • The bake reuses the studio view's own material shader (from the materials work in progress), so the game and the studio can't drift apart.
  • Kit characters (decision 14) get hand-placed seams from their template, not auto-unwrap, since the template is designed once anyway.
  • Atlas mode (B) is added when a project's texture budget check fails. That's the tripwire, and D is where this ends up.

What the research says

  • Turning any 3D object into a production asset needs proper UVs and physically based materials kept separate from baked lighting. The bake should capture material only, not studio lighting. arXiv 2604.23629
  • Lighting baked into AI-made textures "fights the engine's lighting in every scene", and UV seams show up on normal maps. Bakes must be lighting-free with padded islands. Tripo
  • The low-poly standard is one material plus a shared palette or gradient atlas. That's Option B's approach, proven in commercial asset packs. 80.lv
  • Unity's glTF importer can silently break normal maps and UV transforms through shader stripping. Keeping textures to plain base colour, roughness and metallic maps is the safest set for both of your targets. Unity glTFast
