How Effects Are Made

Technical 🚪 One-way door High stakes

Fire in the forge, sparks off the anvil, rain, smoke, dust from footsteps, magic, impacts. Effects pass the "needs a tool" test: you judge them only by eye and timing, they look different in each engine, and they quietly cost performance. Godot and three.js both have particle systems with the same ideas (emitters, behaviour over lifetime, sub-emitters), but no shared file format exists, not even a glTF extension. Stylised low-poly games often make effects from moving shapes with scrolling textures rather than clouds of sprites.

Effects as Studio Assets, Compiled to Both Engines

one effect file→ Godot particles (.tres) + fallback→ three.js (three.quarks)colours from the look lab
What it feels like: "/studio add fire to the forge, cosy not raging". The studio builds flames as a few twisting shapes with a scrolling noise texture, adds a handful of spark particles, takes the colours from your current look, and the same file plays in Godot and the web. "Bigger sparks on each hammer strike" adds a burst triggered by the strike.
The studio owns one effect description: emitters, behaviour over lifetime, bursts, and, by default, the stylised kind of effect built from moving shapes (twisting flame meshes, slash arcs, rings) with scrolling noise textures, which suit low-poly and are cheap to draw. It compiles to Godot's particle resources (with the CPU fallback generated automatically for low-end and web) and to three.quarks, an MIT-licensed three.js particle library. Colours come from the look lab, so effects match each look. Baked sprite sheets are only for smoke and explosions. Effects can be triggered by motion events, like each hammer strike.

Works well when

  • One effect, both engines
  • Matches the low-poly look
  • Effects follow the look lab and motion events

Watch out for

  • Two compilers to keep matched
  • three.quarks' file format isn't documented (pin a version)

What it feels like: a mature, free (MIT) effects format with players for Godot and the web. But it's a whole separate system, with no plugin releases to install and unclear Godot web support.

The case against my pick

Owning an effect format means writing and maintaining two compilers, and three.quarks' file format isn't documented, so its updates could break ours. Whether Godot's GPU particles fully work in the web renderer is unsettled (sources disagree, and trails reportedly don't), so the web path may need the CPU fallback more than expected. If effect parity across engines matters most, Effekseer (D) solves it outright, if its plugin builds and passes a web test.

Assumptions and tripwires

  • Assumes shape-based effects plus a few particles cover most of what a low-poly game needs.
  • Assumes three.quarks is pinned to one version, with a round-trip test on every update.
  • First test on the Mac: GPU particles, trails and turbulence in Godot's web renderer.
  • Tripwire: if the two compilers drift (an effect looks clearly different in each engine), try Effekseer for that effect type.

Research context

  • Godot's particle system covers turbulence, collision and sub-emitters, all as plain text resources the studio can write.Godot particle reference
  • Godot's CPU particles are frozen, with a converter from GPU particles for fallbacks.State of particles report
  • three.quarks (MIT) has emitters, behaviours, sub-emitters, trails, batching and a JSON format, though the format isn't documented.three.quarks
  • There's no glTF extension for particles.Khronos registry
  • Effekseer is MIT with Godot and web players, but the Godot plugin has no releases and its web support is unclear.EffekseerForGodot4EffekseerForWebGL
  • Stylised games favour effects built from shapes with scrolling textures for control and low overdraw.RealTimeVFX
  • On phones and the web, effects cost fill rate, not particle count.Snap Lens Studio
  • Sources disagree on whether Godot's GPU particles work in the web renderer; trails reportedly don't.GPU particles in Godot 4.0bugnet

Where sources disagree

Godot's own blog says GPU particles work in both renderers; others say the web renderer can't run compute-based particles. A one-hour test on the Mac settles it before anything is built on it.
