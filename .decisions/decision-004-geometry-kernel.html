Geometry Kernel Strategy

Technical 🚪 One-way door High stakes

The kernel is the math engine that actually executes box(), union(), round() from your op graph and produces real geometry. It sets a ceiling on what the studio can make at all — and how often an AI-issued operation silently produces garbage. "General-purpose" pulls in three directions at once: watertight solids (booleans), editable polygon meshes (extrude, bevel, subdivide — characters and game assets), and precise CAD surfaces (fillets, STEP export). No single library does all three well in a browser.

Use Manifold for everything. It's tiny, fast, actively maintained, and trusted by Blender and OpenSCAD for booleans. It even carries UVs and material IDs through operations and can build shapes from distance fields. But it only works on closed, watertight solids — you can't drag a single edge, extrude a face loop, or model an open cloth panel. Great for chairs and buildings; dead end for characters.

Works well when

  • Weeks 1–3: furniture, props, architecture blockouts
  • Guaranteed-valid output — the AI can't make a leaky mesh

Watch out for

  • No polygon-level editing at all
  • No fillets/NURBS/STEP
  • WASM build is single-threaded

Make the industrial CAD kernel (the open-source cousin of what SolidWorks uses) the primary engine. You get exact curved surfaces, fillets, shells and STEP export — real engineering precision. But it's 20–50× heavier than Manifold, the classic opencascade.js wrapper stalled in 2023 (use replicad or occt-wasm instead), fillets fail in famously finicky ways, and it's the wrong tool for anything organic.

Works well when

  • STEP/IGES round-tripping is required

  • Multi-MB load; memory pressure on 8 GB
  • No organic or poly modeling

Define one GeometryKernel interface and plug engines into it. Manifold handles solids and booleans from day one; a small half-edge mesh you write in TypeScript handles polygon edits (no maintained JS library exists); OpenSubdiv's WASM port adds smooth subdivision; OCCT is lazy-loaded in a worker only when a CAD op (fillet, STEP) runs. The op graph doesn't care which engine ran — bitbybit.dev ships exactly this three-kernel pattern today.

Works well when

  • "General-purpose" is real but staged
  • You want only ~200 KB loaded until a CAD op is used
  • Each kernel is swappable without touching the op graph

Watch out for

  • Converting between kernels (mesh ↔ B-rep) is lossy one-way
  • Writing a half-edge mesh is ~1–2 weeks of careful work
  • Ops must declare kernel + allowed inputs clearly

The case against my pick

Three kernels means three sets of failure modes, and the seams between them are where bugs live: a mesh edited in EditMesh may no longer be watertight for Manifold, and nothing converts a mesh back into exact CAD surfaces. Writing your own half-edge mesh is real geometry-processing work that an LLM-assisted solo developer can get subtly wrong (non-manifold edges, flipped normals). A narrower product — Manifold-only for the first months (Option A) — would let you prove the AI loop before paying any of that complexity, and the interface could be added later.

This recommendation assumes

  • Stage it: weeks 1–3 Manifold only behind the interface; EditMesh when the first mesh-edit op is needed; OpenSubdiv and OCCT only when a benchmark task demands them
  • Kernel conversions are explicit ops (toEditMesh, toSolid with a validity check), never silent
  • All kernels run in a Web Worker in the browser and in-process in Node — same interface
  • Tripwire: if Manifold's "scratch-mark" boolean artifacts show up in >5% of benchmark runs, add a mesh-repair pass or evaluate OCCT booleans for those ops

What the research says

  • Manifold: guaranteed-manifold booleans, hull, Minkowski, SDF levelSet, refine/smoothing; carries UVs and per-face IDs through ops; manual .delete(); WASM build is serial-only. Manifold README JS guide
  • manifold-3d v3.5.4 (Sept 2026): ~541 KB raw / ~197 KB compressed WASM. Used by OpenSCAD (default backend since Aug 2025), Blender 4.5's Manifold boolean solver, Godot, Babylon.js. npm Blender 4.5
  • Blender users report occasional "scratch marks" in Manifold differences. devtalk
  • opencascade.js: last push Aug 2023, pinned to OCCT 7.6.2; full WASM 48.9 MB (~9 MB brotli). replicad v1.2.0 (Oct 2026) and occt-wasm (~4 MB brotli) are the live options. opencascade.js replicad occt-wasm
  • OCCT fillets: IsDone() can be true on wrong results; fail when edges shorter than radius. OCCT tracker
  • bitbybit.dev runs OCCT, Manifold and JSCAD side by side, each with a worker variant, in Node and browser. bitbybit
  • No maintained JS/TS half-edge poly-modeling library (geometry-processing-js dormant since 2021); three-bvh-csg is preview-grade and points to Manifold for robust output. geometry-processing-js three-bvh-csg
  • OpenSubdiv WASM port (~60 KB gz, Catmull-Clark levels 1–5) exists but is very young (v0.2.0). opensubdiv-wasm
  • Rust: Fornjot archived ~June 2026; truck active (B-rep, booleans, STEP) but no documented fillets. Fornjot truck
  • Export pipeline: glTF-Transform and meshoptimizer are healthy, safe picks. glTF-Transform

Where experts disagree

CAD people say start from B-rep because you can always tessellate down but never recover exact surfaces from a mesh. Game/DCC people say meshes are the universal currency and B-rep is a niche. The resolution for a general-purpose tool is the one Blender itself reached (mesh-first, Manifold for booleans) plus a CAD lane for the subset of work that needs precision — which is what Option C stages.
