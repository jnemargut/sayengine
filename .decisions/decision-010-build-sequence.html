Build the thinnest possible end-to-end path first: a handful of ops, a 5-command CLI, a bare skill, and a bare browser view that just shows whatever the engine holds. By end of week 2 you can type /studio make a walnut stool and watch it appear. Every week after thickens one layer, driven by what the stool and its benchmarks actually exposed — proposals and review in week 4, the polished Soft Premium workspace in week 5.

Works well when

  • You build with Claude Code — the skill improves the skill
  • Every later layer is shaped by real failures

Watch out for

  • Week-2 UI looks rough — resist polishing early
  • Shortcuts in the slice must be marked and paid back

The case against my pick

Vertical slices tempt you to cut corners in the foundation — and three of your decisions (the change log, the op graph with named anchors, the kernel interface) are one-way doors where a sloppy week-1 version becomes the permanent version. "Thicken later" often means "never". Engine-first (D) protects those foundations; benchmark-first (C) protects against building the wrong thing. Mitigation built into B: the slice uses the real record/commit format and real anchors from day one — only the number of ops, CLI commands and UI polish are thin.

This recommendation assumes

  • Week 1 implements the real Scene IR and commit format (one-way doors), just with few ops — no throwaway data model
  • The stool benchmark from Option C is the slice's acceptance test, and the harness lands in week 3
  • You build with Claude Code ~full-time; estimates are prototype estimates, not production
  • The bare view in week 2 is a Three.js page subscribed to the daemon over websocket — no panels yet
  • Tripwire: if the stool isn't appearing end-to-end by day 12, stop adding features and cut scope until it does

Where experts disagree

The "walking skeleton" camp (thin end-to-end first) argues you learn the real requirements only by running the whole loop; the "foundations first" camp argues data models are the hardest thing to change later. You've already settled the data model through Decisions 2–4 in detail, which removes most of the foundations camp's worry — so the skeleton approach gets the benefit without the usual cost.
