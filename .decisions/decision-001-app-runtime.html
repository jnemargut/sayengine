Where the App Runs

Technical 🚪 One-way door High stakes

Before anything else: does your studio live in a browser tab, in a lightweight desktop wrapper (Tauri), in a heavier desktop wrapper (Electron), or as a fully native app? This sets how much memory geometry can use, whether you can save into real folders, how consistent 3D rendering is across machines, and — critically for an AI-first tool — whether an agent can run the whole modeling engine headless (no window at all) for benchmarks and automated self-correction. The key insight from research: the most important part isn't the shell, it's keeping the engine independent of the shell.

Works well when

  • Solo dev on 8GB — zero install, instant reload, Chrome DevTools

A small desktop app: your React UI runs inside the operating system's built-in browser engine, with a Rust backend for files and native code. It's lean on disk and lets you call native geometry libraries from Rust. The catch for a 3D tool: each OS uses a different browser engine, so your viewport renders three slightly different ways, and WebGPU availability depends on the user's OS version.

Works well when

  • Download size matters (3–10× smaller than Electron)
  • You want a Rust path to native kernels (OCCT, Parasolid-class) later
  • You're comfortable writing some Rust

Watch out for

  • macOS WebGPU only on macOS 26+; Linux WebKitGTK effectively WebGL-only + GPU bugs
  • No WebDriver automation on macOS — painful for agent-driven UI testing on your M2
  • Idle-RAM savings vs Electron are small (~15%) in measurements

Write the whole application natively — Rust with the wgpu graphics library (or C++ with Qt). This is the road to Blender-class performance: unlimited memory, multithreaded geometry, direct GPU access. Rerun proves a Rust/wgpu app can also compile to the web.   • UI toolkit work (panels, inspectors, text) is all on you

The case against my pick

"General-purpose, production-ready, all outputs" is ultimately a desktop-class workload: multi-gigabyte scenes, native FBX/USD SDKs, real project folders, and GPU memory beyond what a browser tab is allowed. Starting in the browser can quietly bake in browser-shaped limits (4 GB WASM memory, Chromium-only file access, sandboxed GPU) that you'll fight later — and some serious tools (Shapr3D, Blender) chose native for exactly that reason. If you already know you'll need an installer within three months, Option C avoids a migration step and gives you one consistent engine from day one.

This recommendation assumes

  • The prototype phase is ~6 weeks and scenes stay well under 4 GB of geometry memory
  • You (and early testers) are fine using Chrome/Edge for the real file workflow
  • The engine package is enforced DOM-free from commit one (a lint rule + a Node test run in CI)
  • Tripwire: revisit if you need native SDKs (FBX, USD C++) or scenes approach 2–3 GB → wrap in Electron

What the research says

  • WebGPU now ships in Chrome/Edge, Safari 26 and Firefox (Windows; Apple Silicon since 145) — but plan a WebGL fallback for everyone else. web.dev
  • Inside Tauri on macOS, WKWebView only exposes WebGPU when the OS enables it by default (macOS 26+); Safari flags don't carry over. WebKit Bugzilla tauri #6381
  • Tauri on Linux: WebKitGTK GPU issues (blank windows, flicker, slow WebGL paths); Tauri's WebDriver testing doesn't support macOS. Tauri docs Tauri WebDriver
  • Measured: Tauri 57 MB vs Electron 323 MB on disk, but only 109 vs 128 MB idle RAM. Better Stack Hopp
  • wasm32 caps at 4 GB; Memory64 shipped in Chrome/Firefox but is 10–100%+ slower — use only if you truly need >4 GB. V8 SpiderMonkey
  • WASM threads need SharedArrayBuffer → cross-origin isolation (COOP/COEP headers). StackBlitz
  • Folder read/write via showDirectoryPicker is Chromium-only; OPFS works everywhere. web.dev
  • Manifold runs in plain Node (import Module from 'manifold-3d') and has a CLI — the engine can run fully headless; remember manual .delete(). Manifold docs
  • Precedents: Figma's C++→WASM engine in the browser (3× faster loads); Onshape full CAD in-browser (cloud kernel); Plasticity is a TypeScript/three.js-derived desktop CAD; Shapr3D chose fully native. Figma Onshape Plasticity Shapr3D
  • Rerun ships one wgpu renderer native + web with WebGPU→WebGL fallback tiers — the realistic dual-path pattern. Rerun

Where experts disagree

Tauri advocates point to 3–10× smaller downloads and a Rust path to native kernels; Electron advocates point to one identical Chromium and mature automation. For a 3D viewport specifically, rendering consistency and testability win — which is why the disagreement mostly resolves toward Electron if you go desktop. The deciding condition: whether you'll write Rust anyway or stay all-TypeScript.
