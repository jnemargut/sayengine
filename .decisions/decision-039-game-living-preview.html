Living Preview for a Game

Visual 🔁 Two-way door Medium stakes

In decision-kit's product skills, preview.html is a mockup of the app that absorbs each decision, so by the end you're looking at the app itself. For a game made toy-first (decision 37), what you're making is partly something to play and partly a plan. This decides what the one page that grows with a game's decisions is.

The preview is a one-page game design in the style designers like Stone Librande use: pitch, pillars, controls, loop, scope, and later the look and world. In the middle, a play window holds the latest build. Each decision fills its block, so the page is both the plan and the game so far. The ledger strip across the top shows what's decided, what's pending, and links to each page. Undecided blocks stay grey and labelled, never filled with a guess.

Works well when

  • You want the "why" and the game in one place
  • Toy-first: there's always a build to show
  • Showing someone the game in 30 seconds

Watch out for

  • The build must stay small enough to embed

The case against my pick

A one-page design is still a document, and for a toy-first road the honest preview is the toy itself (B): pillars and loops written next to a build can quietly drift from what the build actually does. Embedding a live build in a page also means rebuilding it whenever a decision changes, which can make the preview stale or slow. If you rarely show games to anyone, B is simpler and can't lie.

Assumptions and tripwires

  • Assumes the build skill exports a small web build after each playable step, which the page embeds.
  • Assumes undecided blocks stay grey and say which step decides them, so the page never shows a guess.
  • Tripwire: if the written loop or controls disagree with the build at a playtest, the playtest skill flags the block for a re-decision.
