Scene Source of Truth & Change Model

Technical 🚪 One-way door High stakes

This is the "save file and history" brain of the studio. Every feature that sets it apart — undo, AI proposals you can accept or reject, three roof variants side-by-side, "what did the AI change?", rolling back an agent's work, two agents working at once — is really a question about how changes to the scene are stored. Pick the wrong shape here and every one of those features becomes a fight. It runs inside the headless engine you just chose, so the AI and the UI share it exactly.

The scene is one big JSON object in a state store; each change records "how to undo it". Dead simple — you'd have it working in a day. But history is a single straight line: there's no natural home for "the AI's three roof proposals" or "branch off and try something", so you'd bolt those on later by copying entire scenes.

Works well when

  • You want the viewport milestone done this week
  • History is "undo the last few things", nothing more

Watch out for

  • Proposals/variants become whole-scene copies — memory-heavy with meshes
  • No audit trail of what the AI did; refactor later touches everything

Records + Branching Change Log

// every tool call = one transaction commit c7 parent:c6 author:"agent:claude" tool: "setParam" obj_chair.legThickness 0.04→0.03 patches: [fwd], inverse: [inv] blobs: mesh#9f2a… (content hash)
Mesh blob store (by hash)
Snapshots every N commits
The scene is a flat table of records with permanent IDs (objects, materials, parameters). Every AI tool call or human edit is one transaction that records its forward and reverse patches, who made it, and why. Commits form a git-like graph: AI proposals are just branches you can preview, compare, and merge or throw away. Heavy meshes live in a separate store keyed by content hash, so branching costs almost nothing. This is the Onshape "microversion" pattern plus Cursor-style checkpoints.

Works well when

  • Proposals, variants and accept/reject are core UX (they are)
  • You want a full audit log of every AI action — doubles as benchmark data
  • Undo, history and proposal-diff all come from one mechanism

Watch out for

  • ~1–2 extra weeks of design up front vs Option A
  • Schema changes need migrations; old commits must replay (snapshots cap this)
  • Merging two branches that touched the same object needs a conflict rule

Use a CRDT — a data structure designed so multiple editors can change it at the same time and always merge cleanly. Loro 1.x gives you fork, checkout-any-version and merge for free, which maps nicely onto proposals and multi-agent work. The catch: "always merges" doesn't mean "merges into a valid chair" — two agents can produce a legal merge that's geometrically nonsense, and you lose a single place to enforce rules.

Works well when

  • Real-time multi-agent / multi-human editing is a near-term goal
  • Offline + peer-to-peer sync matters
  • You want branching without writing it yourself

Watch out for

  • Validation is harder — merges bypass tool-level checks
  • Binary meshes must live outside anyway (history bloat)
  • Figma, tldraw, Onshape all chose not to use a pure CRDT

Make Pixar's Universal Scene Description the live in-memory model. USD natively has layers (stack an AI proposal on top of the real scene), variant sets (roof = craftsman | flat), and references — conceptually a beautiful fit. In practice its browser builds are several MB, need special server headers, and are aimed at viewing rather than editing, and USD has no native notion of undo history or semantic parameters.

Works well when

  • Film/VFX pipeline interop is the primary market
  • Huge composed scenes with references are the core use case

Watch out for

  • Browser USD runtimes target viewing; editing/export support is immature
  • Multi-MB WASM, threaded → COOP/COEP headers required
  • History, transactions, semantics still need to be built on top

The case against my pick

Option B means building your own mini version-control system before you've proven anyone wants AI proposals — event-sourced systems pay a lasting "tax" (every old change must still replay after schema changes, and snapshots become their own versioned format). Loro (Option C) already gives you fork, checkout and merge, battle-tested, for free; if multi-agent concurrent editing turns out to matter early, you may end up re-implementing half a CRDT inside B. And Option A is genuinely enough for weeks 1–2 — you could start there and migrate once proposals are real.

This recommendation assumes

  • Edits flow through typed tool calls one at a time (a central authority), not simultaneous peer-to-peer editing
  • AI proposals/variants are a core differentiator, not a nice-to-have
  • Meshes are stored by content hash outside the log, with snapshots every N commits to cap replay cost
  • Tripwire: if you need two agents editing the same object simultaneously with automatic merge, revisit Loro as the storage layer underneath the same record API

What the research says

  • Figma isn't a true CRDT: a central server is the authority and properties are effectively last-writer-wins, with the server rejecting invalid tree changes. Figma Engineering
  • tldraw sync is server-authoritative with schema validation and migrations so different client versions interoperate. tldraw docs
  • Onshape: every edit is an immutable "microversion" pointing to its parent; workspaces are branches; undo is a new inverse microversion; conflicting merges surface as red errors to repair. Onshape merging
  • Immer's produceWithPatches returns forward + inverse patches — the same patches can be undo, operation log and proposal diff. Immer docs
  • Loro 1.0 offers checkout(version), fork() and merge-by-import; shallow snapshots are 70–90% smaller. Loro shallow snapshots
  • Automerge 3 cut memory >10× (one doc: 17 hours → 9 seconds to load). Automerge
  • Large binaries don't belong in a CRDT — store a hash in the doc, bytes in a content-addressed blob store. Syncline
  • Event-sourcing tax: events live forever, so every old version must be upcast on replay; snapshots need their own schema version. Vivian Voss
  • OpenUSD 26.05 runs in-browser via Needle's WASM runtime (threaded, needs COOP/COEP), but editing-and-export-back is "not yet supported". Needle
  • AI prior art: tldraw's agent kit uses typed action classes; Figma Make keeps AI edits uncommitted until Apply — yet users report lost work; Cursor's per-change Keep/Undo review is fiercely defended by users. tldraw agent Figma forum Cursor forum

Where experts disagree

Local-first advocates say CRDTs (Loro/Automerge) are now fast enough to be the default for any collaborative document. The "you might not need a CRDT" camp — and the products that actually ship (Figma, tldraw, Linear, Onshape) — say: if there's one authority anyway, an authoritative log is simpler and validates better. Here the deciding condition is whether AI agents edit concurrently and offline (CRDT) or through one validated tool pipeline (log). The architecture so far says the latter.
